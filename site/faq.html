FAQ

Short answers. The project's docs/FAQ.md and wiki FAQ go deeper on most of these.

What this is

Is this an emulator?

No, and that's the whole point. An emulator runs the retail ROM by pretending to be an N64, which works but can't change the game — the game inside it is compiled MIPS machine code. This is built from the decompilation: the game as editable C, compiled to a normal executable for your OS. No core, no plugin, no ROM loaded at runtime.

Is this the Xbox 360 remaster, or the cancelled XBLA build?

Neither. Those are separate codebases. This is the Nintendo 64 game, from its decompilation.

How is this different from a source port like Ship of Harkinian?

Same idea, different game. A decompilation gets turned into a native program with a modern platform layer. Ship of Harkinian is Ocarina of Time; this one is GoldenEye.

Does it need Wine, Proton or WSL?

No. Every platform gets a real native binary. The Windows build uses mingw-w64, with no MSYS2, Cygwin or WSL anywhere near it.

Downloads and installing

Where can I download it?

You can't. There is no prebuilt binary, no installer with the game in it, and no release of any kind — this repository has zero tags and zero GitHub Releases. A built copy of this port has the entire game compiled into it, which is not this project's to hand out. You build it yourself from your own copy. Install walks through it.

If you find a "GoldenEye-Native" download somewhere, it did not come from here. That includes executables pulled from GitHub Actions runs and third-party reposts.

How do I install it, and how long does it take?

One installer per platform: double-click Install on Mac on macOS, or run bash tools/install.sh on macOS/Linux, or tools\install.ps1 in PowerShell on Windows. You need about 4 GB free, an internet connection for the first run, and 10 to 40 minutes. That happens once. Step by step.

Is there a one-click Windows installer?

It exists as an unsigned release candidate and is not published. There is no official Windows download and no release automation — the CI workflow validates the candidate inside the runner and deliberately does not upload it. Until this repository's Releases page lists a coordinated package, use the developer path.

The installer stopped partway. Do I start over?

No — run it again. Every step checks whether its own output already exists and skips it, so re-running resumes. On Linux, a missing system dependency makes the installer print the exact package-manager command and stop rather than running sudo itself; install that package and re-run.

How do I know the build worked?

Every build group reports 0 failed. Any name in a FAILED: line is a real regression, not an expected one. Then the launcher opens.

The ROM

Do I need the ROM?

Yes — your own legal copy of the NTSC (US) cartridge, dumped to a file. Nothing in this repository contains game data and nothing ever will. Every texture, model, animation, sound bank and level layout is read out of your dump once, at build time, and emitted as C.

This site will not tell you where to get one, and no page here ever will — not out of squeamishness, but because downloading a ROM is an unauthorised reproduction even if you own the cartridge, which is one of the few genuinely settled points in the legal answer below. Linking to one would put the project on the wrong side of the one line it can actually be sure about.

What exactly does the build expect?

12,582,912 bytes exactly, big-endian z64, header magic 80371240, internal name GOLDENEYE, SHA-1 abe01e4aeb033b6c0836819f549c791b26cfde83. A .n64 or .v64 extension, or a header of 37804012, means byte-swapped. The macOS and Linux installers accept those byte orders; the Windows setup app recognises but refuses them, because the no-copy installer will not write a converted second file to your disk. Details.

Does the installer copy or upload my ROM?

Nothing is ever uploaded, and your original file is never moved or modified. Whether a copy is made depends on the platform:

  • Windows. The setup app reads your big-endian .z64 where it sits and verifies its SHA-1 in place. No copy.
  • macOS and Linux. tools/install.sh asks first (“convert and copy this into roms/?”), then writes one verified copy to roms/ge007.u.z64 inside the project folder and links the build at that. Your original is left exactly where it was.

Copying is currently done even when the dump is already the right byte order and needs no conversion. That is tracked as issue #80. Either way, the extraction and the build happen entirely on your machine.

Does the game still need the ROM after it is built?

No. The build reads it once. What you run afterwards never touches it.

Controls

Does it support mouse and keyboard?

Yes, and it's the default. Mouse look with sensitivity and Y-invert, WASD to move, ESC to release the cursor. A gamepad (DualSense, DualShock 4, Xbox, Switch Pro, 8BitDo) works alongside it rather than replacing it — whichever input is being held wins, so plugging one in never takes the keyboard away. Both analogue sticks are live, which the N64 controller could never do.

What is "modern" versus "classic" mouse?

modern is the default: mouse travel changes camera angles directly, with no stick acceleration, turn-speed cap or carried surplus motion. classic keeps the original mouse-to-N64-stick mapping. Vehicles, network sessions and scripted or replay input stay on Classic N64 regardless of the setting.

Is there a crouch key?

Yes, and the original doesn't have one — retail crouch means holding aim, pushing down, then releasing aim while staying low. Here it's C or Left Shift, with V to stand. The original gesture still works if you're attached to it.

Can I rebind everything?

Six gamepad actions can be rebound today — fire, aim, use, next weapon, previous weapon and pause — and bindings are per player, which is what makes a mixed set of controllers workable in split screen. Complete independent keyboard, mouse and gamepad rebinding is not done yet; it is issue #63. One trap: button names are positional, so a always means the physically bottom face button, including on a Nintendo pad where it is printed B. Reference.

Performance and picture

How fast does it run? Can it go above 60fps?

Uncapped, it measures 486 fps on an Apple M1 — Dam, 1280×960, three runs, with the game itself ticking at the 60 fields per second it should (README.md). docs/CONFIGURATION.md records 456 fps for the same machine on the real clock. But GoldenEye's gameplay logic is tied to its frame step — weapon fire rates, guard reactions and turret behaviour advance per tick, not per second — so rendering faster also runs the game faster. framerate=30 pairs with a tick divider to run the simulation at its authored cadence while rendering stays smooth.

The correct fix is a fixed simulation tick with interpolated rendering, and the project names it as such — docs/VISION.md calls the tick coupling “the most consequential open problem in the project”. It is not scheduled and has no tracking issue. It needs every visually interpolated quantity identified, and the game stores plenty of state that must not be interpolated, so getting the list wrong produces jitter that is harder to diagnose than the original problem. Until it lands, 60fps is the honest ceiling for unchanged gameplay.

Why does it refuse a frame cap above 60?

Because a capped rate above 60 is either wrong or pointless, with no third case. On the default synthetic clock a cap above 60 runs the world too fast; on the real clock a cap never free-runs, so 120 still delivers 60. framerate = off is the high-refresh setting and switches to the real timebase as part of the same choice. The measurements.

Is there widescreen?

Resolution and aspect are fully configurable, but changing the window aspect does not widen the field of view today — the renderer fits the 4:3 view into whatever shape the window is. The widescreen key fills the real window at its own aspect for single player; split-screen's per-viewport aspect is untouched either way. True aspect-aware widescreen is not done: docs/VISION.md item 2 records that whether widescreen widens the horizontal field or stretches a 4:3 image has not been measured. Use fov if you want to genuinely see more.

Can it run at 4K?

Internal resolution is arbitrary and supersampling is available, so yes. Whether it is a good idea depends on the frame-timing answer above.

Why do crate explosions look like coloured confetti?

That is an RGBA16 byte-order symptom with its own gate, GETV_RGBA16BE, which defaults to the corrected mode. It is not the paintball cheat. It gets reported often enough to be worth naming.

Multiplayer

Is multiplayer online, or over LAN?

Split screen works today, with all 64 characters, the radar and the full multiplayer setup. A LAN session exists and is alpha, and whether the approach can work at all is honestly disputed inside the project's own docs: one document argues for a lockstep model, another argues against it from measurements — both are kept rather than picking a winner prematurely. Online play sits downstream of the frame-timing work. Where that stands.

Can two people play the single-player campaign?

Partly, and it's alpha. Two to four players spawn into a solo mission with its own geometry, props and objectives, and everyone moves and renders — movement was verified over 6,001 frames against a no-input control. What isn't adapted yet is everything the campaign authors around a single Bond: objectives, AI and cutscenes.

Two people have sat down and played it at two pads — that session is how the friendly-fire problem was found, because no scripted run was ever going to point one player's gun at another's back. Friendly fire is the one rule still not measured directly (docs/COOP.md).

Note that docs/VISION.md and docs/FAQ.md still carry an older conclusion that players do not move. That was a measurement bug in the accessor, corrected in docs/ROADMAP.md §M4; the two older documents are stale. Recorded here rather than quietly reconciled.

Modding

Can I mod it?

Three ways, none needing a rebuild: Lua scripts in mods/ (onFrame, onPlayerSpawn, onWeaponFire, plus a read API into live game state), roughly 275 GETV_* behaviour gates, and goldeneye.cfg. Editing the source is a fourth way, but that one does need a rebuild. HD texture replacement is implemented but unverified, and is off by default.

How do I write one?

Copy mods/crt_screen, rename it, and edit it. A mod is a folder with a mod.lua in it — that is the entire rule. Everything found is loaded at startup; a folder without a mod.lua is skipped silently. The launcher's Mods page gives each one a checkbox. The CRT mod is deliberately the example because it is a real, visible feature rather than a toy.

Is there a mod-pack download hub?

Not yet. Mods live in the repository's own mods/ directory today and are shared the same way the project is: clone it, drop one in, or open a pull request. A launcher setting points at whichever mods directory you choose.

Platforms

Does it run on Steam Deck, Raspberry Pi, Android or iPhone?

Linux builds run where Linux runs, so a Deck is a Linux build.

The other three are further along than “not yet”, and further from “working” than that sounds. README.md calls them bring-up, not products:

  • tvOS (Apple TV) builds, signs and deploys to real hardware, on GL ES or Metal.
  • iOS builds against Metal, and there is a Simulator build that needs no paired hardware. Deploying to an actual device does need one.
  • Android's port layer builds for arm64 GL ES and carries on-screen touch controls as a virtual pad — but it has never been run. It is not a running game.

Nothing mobile is distributed, and none of it is a thing you can go and play today.

OpenGL or Metal on macOS?

Both exist; OpenGL is the default and is what the installer builds. The launcher's Video page remembers a renderer choice separately from profiles, rules and saves, and a renderer that is missing or unavailable is disabled rather than offered. The Metal build is a separate build directory. How to build it.

Settings, saves and privacy

Where are my settings and saves?

Settings are goldeneye.cfg and saves are eeprom.bin, both in the platform user-data directory — %APPDATA%\Goldeneye-Native\ on Windows, ~/Library/Application Support/Goldeneye-Native/ on macOS, ~/.local/share/Goldeneye-Native/ on Linux. The exact paths in use are printed at startup, which is the authoritative answer for your machine. Details.

Does the launcher overwrite my config file?

No. It reads your resolved settings and shows them, and applies your choices to that launch. It never writes goldeneye.cfg. Put a setting in the file if you want it to persist between sessions.

Does any of this phone home?

No. This website has no analytics, no trackers and no external requests — system fonts only and every image local. The game has a PropRecord allocator telemetry gate, but it is a local diagnostic that is silent by default and writes JSON Lines on your own machine; it sends nothing anywhere. The console's command history is bounded to the running process and is never written to your config or to diagnostic output.

Licensing

What's the licence? Is “MIT” the right word for this project?

No — “source available” is the accurate one. There is a root LICENSE and it is MIT, but MIT is a grant the project can only make over work the project owns. Four different things live in this tree and only the first is covered.

1. This project's own code — MIT. Per NOTICE: the platform layer under getv/port/ excluding the fetched third-party sources, the build scripts, tools/, and the documentation.

2. Inherited third-party port code — unresolved. The Fast3D renderer and the audio mixer came through sm64ex from Emill/n64-fast3d-engine. sm64ex ships no licence file, and the Emill notice it reproduces prohibits binary redistribution. Two headers (configfile.h, fs/fs.h) are verbatim sm64ex copies with the same problem. Because it is unresolved, this repository does not distribute those files — tools/fetch-thirdparty.sh fetches them from upstream at a pinned commit and applies the project's changes as a patch series.

3. The decompiled game source — upstream's situation, not ours to license. n64decomp/007 publishes no licence file, and 58 files under its src/libultra/ carry Silicon Graphics proprietary notices. It is not distributed here either; it is fetched separately.

4. Game data — never, under any licence. No ROM, no extracted assets, no textures, no audio, no level data, in the tree or in its history.

None of this is glossed. The itemised account, with what was checked and how, is in docs/LICENSING.md; the unresolved renderer question is its section 4. This is a factual record, not legal advice.

Is it legal for me to build and play this? (United States)

This project cannot answer that for you, and anyone giving you a confident yes or no is overstating what is actually settled. What follows is a factual account of which parts are settled and which are not, under US law. It is not legal advice.

Settled — not seriously disputed by anyone:

  • Distributing is infringement. The ROM, extracted assets, generated asset source, or a built binary with the game compiled into it. That is precisely why this project ships none of them, and why there is no download.
  • Downloading a ROM is an unauthorised reproduction — even if you own the cartridge. Owning one copy does not entitle you to receive another from a stranger. “I own it, so I can download it” is the most common misconception in this space and it has no statutory basis.
  • GoldenEye 007 is in copyright and will be for decades. There is no public-domain angle here.

Not settled — and this is the honest reason we will not tell you it is fine:

  • Dumping a cartridge you own. No US court has held that it is lawful, and no statute plainly says so. People point to 17 U.S.C. §117(a)(2), which lets the owner of a copy of a computer program make an archival copy — but its scope is narrow, courts have read “owner” restrictively where a licence is involved, and it has never been applied to a game-cartridge dump in a controlling decision. Fair use (§107) is a fact-specific defence raised after the fact, not permission granted in advance.
  • The decompilation itself. Sega v. Accolade (9th Cir. 1992) and Sony v. Connectix (9th Cir. 2000) protected reverse engineering as fair use, and they are the cases usually cited here — but both concerned intermediate copying to achieve interoperability. A decompilation that reproduces the program's own expression is a different question and has not been tested. n64decomp/007 ships no licence file at all, which docs/LICENSING.md §5 records as unresolved rather than resolved in anyone's favour.

What is true in practice, which is not the same thing. Enforcement in this area has gone after distribution — sites hosting ROMs, sellers of preloaded devices — rather than individuals dumping a cartridge they own for their own use. That is an observation about what rightsholders have actually done. It is not a statement that private dumping is lawful, and it is not a prediction about anyone's future behaviour.

What this project does, factually: it distributes no game data of any kind, the build reads a file you already have and leaves it untouched, and everything it produces stays on your machine. Nothing here uploads your dump, copies it, or sends it anywhere.

If the answer matters to you — because you are doing anything beyond playing, on your own machine, a game you already own — ask a lawyer. This project deliberately reaches no legal conclusion, in docs/LICENSING.md or here.

Why not just ship a binary and read the ROM at runtime?

Because this port compiles the extracted assets directly into the executable rather than loading them at runtime. Changing that would mean re-architecting asset delivery to load from disk, which is a significant piece of work and is not currently planned.

Something is wrong

Is it a known problem?

Check Known bugs & limitations first. A number of things that look like bugs are documented constraints — the widescreen field of view, the frame-rate ceiling, six settings that parse and do nothing, and four traps that each look like a broken feature.

How do I report it?

Two ways, both fine. If you use a coding agent, this project ships its own workflows and that is the recommended route — see Help from an agent. Otherwise the guided issue forms ask for the same information. Have your commit (git rev-parse --short HEAD), platform, renderer, settings, exact steps, and whether it happens on clean main.

Never attach a ROM, a save file, base.zip, extracted game data or your built executable to an issue, a pull request or a chat message. Text logs, error messages and screenshots of the running game are exactly what is useful.

I found a security problem.

Use the security policy privately instead of opening a public issue.
