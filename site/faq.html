Questions people actually ask

The short version. The project's docs/FAQ.md and wiki FAQ go deeper on most of these.

Is this an emulator?

No, and that's the whole point. An emulator runs the retail ROM by pretending to be an N64, which works but can't change the game — the game inside it is compiled MIPS machine code. This is built from the decompilation: the game as editable C, compiled to a normal executable for your OS. No core, no plugin, no ROM loaded at runtime.

Is this the Xbox 360 remaster, or the cancelled XBLA build?

Neither. Those are separate codebases. This is the Nintendo 64 game, from its decompilation.

How is this different from a source port like Ship of Harkinian?

Same idea, different game. A decompilation gets turned into a native program with a modern platform layer. Ship of Harkinian is Ocarina of Time; this one is GoldenEye.

Do I need the ROM?

Yes — your own legal copy of the NTSC (US) cartridge. Nothing in this repository contains game data and nothing ever will. Every texture, model, animation, sound bank and level layout is read out of your dump once, at build time, and emitted as C.

Does it support mouse and keyboard?

Yes, and it's the default. Mouse look with sensitivity and Y-invert, WASD to move, ESC to release the cursor. A gamepad (DualSense, DualShock 4, Xbox, Switch Pro, 8BitDo) works alongside it rather than replacing it — whichever input is being held wins.

Is there a crouch key?

Yes, and the original doesn't have one — retail crouch means holding aim, pushing down, then releasing aim while staying low. Here it's C or Left Shift, with V to stand. The original gesture still works if you're attached to it.

How fast does it run? Can it go above 60fps?

Uncapped, it measures 354–562 fps on an Apple Silicon Mac. But GoldenEye's gameplay logic is tied to its frame step — weapon fire rates, guard reactions and turret behaviour advance per tick, not per second — so rendering faster also runs the game faster. framerate=30 pairs with a tick divider to run the simulation at its authored cadence while rendering stays smooth. A fixed simulation tick with interpolated rendering is the correct fix and is on the roadmap; until it lands, 60fps is the honest ceiling for unchanged gameplay.

Is there widescreen?

Resolution and aspect are fully configurable, but changing the window aspect does not widen the field of view today — the renderer fits the 4:3 view into whatever shape the window is. True aspect-aware widescreen is a roadmap item.

Is multiplayer online, or over LAN?

Split screen works today. A LAN session exists and is alpha, and whether the approach can work at all is honestly disputed inside the project's own docs: one document argues for a lockstep model, another argues against it from measurements — both are kept rather than picking a winner prematurely. Online play sits downstream of the frame-timing work.

Can two people play the single-player campaign?

Partly, and it's alpha. Two to four players spawn into a solo mission with its own geometry, props and objectives, and everyone moves and renders. What isn't adapted yet is everything the campaign authors around a single Bond: objectives, AI and cutscenes.

Can I mod it?

Three ways, none needing a rebuild: Lua scripts in mods/ (onFrame, onPlayerSpawn, onWeaponFire, plus a read API into live game state), roughly 275 GETV_* behaviour gates, and the source itself. HD texture replacement is on the roadmap and not implemented yet.

Does it run on Steam Deck, Raspberry Pi, Android or iPhone?

Linux builds run where Linux runs, so a Deck is a Linux build. An Apple TV target builds from this tree as of the Metal backend landing (2026-08-26), with device bring-up next. iOS and Android are not here yet — the groundwork exists (SDL2 underneath, a platform layer already split from the game, a renderer that already targets GLES) but the shipping work doesn't. Nothing mobile is distributed and nothing mobile is claimed as working today.

Does it need Wine, Proton or WSL?

No. Every platform gets a real native binary. The Windows build uses mingw-w64, with no MSYS2, Cygwin or WSL anywhere near it.

What's the licence? Is “MIT” the right word for this project?

No — “source available” is the accurate one. There is a root LICENSE and it is MIT, but MIT is a grant the project can only make over work the project owns. Four different things live in this tree and only the first is covered.

1. This project's own code — MIT. Per NOTICE: the platform layer under getv/port/ excluding the fetched third-party sources, the build scripts, tools/, and the documentation.

2. Inherited third-party port code — unresolved. The Fast3D renderer and the audio mixer came through sm64ex from Emill/n64-fast3d-engine. sm64ex ships no licence file, and the Emill notice it reproduces prohibits binary redistribution. Two headers (configfile.h, fs/fs.h) are verbatim sm64ex copies with the same problem. Because it is unresolved, this repository does not distribute those files — tools/fetch-thirdparty.sh fetches them from upstream at a pinned commit and applies the project's changes as a patch series.

3. The decompiled game source — upstream's situation, not ours to license. n64decomp/007 publishes no licence file, and 58 files under its src/libultra/ carry Silicon Graphics proprietary notices. It is not distributed here either; it is fetched separately.

4. Game data — never, under any licence. No ROM, no extracted assets, no textures, no audio, no level data, in the tree or in its history.

None of this is glossed. The itemised account, with what was checked and how, is in docs/LICENSING.md; the unresolved renderer question is its section 4. This is a factual record, not legal advice.

Where can I download it?

You can't — there is no prebuilt binary, no installer with the game in it, and no release to download. A built binary of this port contains the entire game compiled in, which is not this project's to hand out. You build it yourself from your own copy — Build from source has the steps.
