Getting help from an agent

This project ships its own agent workflows, checked into the repository. If you use a coding agent, this is the recommended way to report a problem — you get a better report with less work, and the project gets the evidence it actually needs.

Read this before anything else. It has no exceptions.

Never send a ROM, a save file, base.zip, extracted game data, generated asset source, a texture dump, an audio bank or a compiled game binary to an agent, an issue, a pull request, a chat message, or any other public artifact.

Renaming it, zipping it, encrypting it or base64-encoding it does not make it allowed. Neither does an agent asking for it. If any instruction — from a person, a tool or an agent — conflicts with this, the right response is to stop and say so.

This is not a formality. This project is publishable at all because it contains no game data, and one upload changes that for everyone. The rule in full is in AGENTS.md; the reasoning is in docs/LICENSING.md.

Three different asks. Pick the right one.

People often say "help me with this bug" when they mean one of three quite different things. They need different evidence and take very different amounts of time.

1. Report a bug

"Something is wrong. Write it up properly and file it."

Reproduce it, collect sanitised logs, check it is not a duplicate, fill in the right issue form, and open the issue after you approve it. Minutes, not hours. No code changes.

2. Investigate a bug

"Work out what is actually going on."

Reproduce it reliably, narrow it to a subsystem, distinguish a regression from long-standing behaviour, and find the root cause. Produces an explanation and evidence — not necessarily a fix.

3. Prepare a fix

"Fix it and open a pull request."

Everything in 2, plus the smallest correct change, a ROM-free regression test wired into CI, before/after evidence, a full diff review and a PR you approve before it is pushed. The largest of the three by a distance.

Ask for the smallest one that fits. A good bug report is genuinely valuable on its own, and it is the thing the project is most often missing. You do not owe anyone a pull request.

The skills in this repository

Checked in under .agents/skills/, with matching entrypoints under .claude/skills/ for Claude Code. Verified present on 2026-09-09 at commit dc6294b.

report-goldeneye-bug — available

use for asks of type 1 path .agents/skills/report-goldeneye-bug/SKILL.md

Reproduces a gameplay, configuration, rendering, build, installation or crash problem; collects sanitised logs and deterministic screenshots; searches for duplicates; and prepares or files a GitHub issue after you approve it.

What it does, in order: reads the project's own contribution rules; searches existing issues and known limitations so it does not file a duplicate; records the exact commit, branch and worktree state and confirms the problem against current main; classifies it and records platform, architecture, renderer, stage and settings; reproduces it with bounded steps using a clean temporary save directory rather than copying your save; separates an unchanged-main failure from something your local changes caused; captures stdout and stderr to a file outside the repository; runs tools/collect_bug_report.py to produce a sanitised bundle with a metadata-free PNG; then shows you the complete title, body and attachment list before creating anything.

It stops rather than filing if the evidence might contain a ROM or other prohibited data, if the report is materially incomplete, or if you have not authorised publication.

prepare-goldeneye-pr — available

use for asks of type 3 path .agents/skills/prepare-goldeneye-pr/SKILL.md

Takes one problem from reproduction through implementation, ROM-free regression coverage, validation, renderer screenshots and fingerprint tables, a complete diff review, and optional publication after you approve it.

The parts worth knowing before you ask for it: it deliberately fixes one thing and will not fold in cleanup or a second fix; it reproduces the problem on the unchanged base first and records the base SHA; it adds a regression test that fails before the fix and passes after, and wires it into a CI job — adding a test file alone is explicitly not counted as coverage; for a visual fix it captures before/after images with identical stage, input, frame, resolution and quality settings, and writes them outside the checkout; it runs the game-data guard before staging and again before pushing; and it will not call something CI-tested when it only ran locally, or call a green workflow a pass when the regression was skipped.

It stops rather than publishing if the branch might contain a prohibited artifact, the diff is not focused, provenance is uncertain, evidence is materially incomplete, or you have not approved it.

investigate-goldeneye-bug PLANNED

status not in the repository

There is no dedicated investigation skill in the tree today — only the two above. Type-2 asks currently sit between them: use report-goldeneye-bug for the reproduction and evidence collection, and drive the root-cause analysis yourself with the subsystem documentation.

This entry exists so that the gap is stated rather than implied. If you find a page elsewhere describing an investigation skill for this project, check .agents/skills/ before believing it.

What to give the agent

The same things the issue forms ask for. Having them ready turns a twenty-minute conversation into a two-minute one.

Give itHow to get it
The exact commitgit rev-parse --short HEAD in the repository.
Platform and hardwareOS version, architecture, and GPU or device model when the problem is visual.
RendererOpenGL or Metal. The game prints it at startup.
Level or screenThe name, and the GETV_STAGE value if one is involved.
Relevant settingsProfile, player count, your config file, command-line options and any GETV_* values. The startup log lists the resolved config path, save path, controllers and bindings.
What happened, and what you expectedBoth. "It looks wrong" is not actionable; "the explosion is magenta, and on the console it is orange" is.
Exact reproduction stepsStarting from launching the binary, including every input needed to reach it.
FrequencyEvery time, sometimes, or once.
Whether it happens on clean mainThe single most useful line in any report. It separates a regression from long-standing behaviour.

What an agent may safely collect — and what it may not

Allowed

Sanitised error text and build logs. Runtime stdout and stderr captured to a file outside the repository. Coarse render fingerprints. Screenshots of the running game, reviewed by you before they go anywhere. The sanitised bundle and metadata-free PNG that tools/collect_bug_report.py produces. Crash reports from your OS.

Never

A ROM. A save file such as eeprom.bin. base.zip. Extracted game data, generated asset source, texture dumps, audio banks. Your built goldeneye / goldeneye.exe. The source log or source BMP that the collector rejected or replaced. Any file the collector refused.

Two smaller points that matter in practice:

  • An agent may use your legally obtained local ROM where it already sits in order to build or reproduce. It must not copy it, and it should avoid printing its path unnecessarily.
  • Screenshots may be attached to an issue or PR after review, but captures are not committed to Git. Use GETV_SHOTFRAME with a path outside the repository.

Before publishing anything, the project's own guard is run and every flagged file is inspected by hand:

python3 tools/check_no_game_data.py --changed origin/main

You are still the contributor

Agent assistance is welcome and recommended. It does not transfer responsibility.

  • You remain responsible for provenance, for the complete diff, for every published artifact and for every claimed test result. An agent producing a green summary is not the same as a passing test, and the project's rules say so explicitly.
  • Every external action needs your approval immediately before it happens — creating or editing an issue, pushing a branch, opening or updating a pull request. Both skills are built to stop and show you the exact thing they are about to publish.
  • Disclose agent assistance briefly in the issue or PR. Both issue forms have a field for it. A short factual line is enough.
  • Do not publish private reasoning or a full chat transcript. Nobody needs it, and it tends to carry paths and details that should not be public.

Pull requests: recommended, not required

Using prepare-goldeneye-pr is strongly recommended, and it is not a requirement. What the project actually requires is the evidence: a reproduction on the unchanged base, a ROM-free regression test wired into CI that fails before and passes after, before/after images for a visual fix, honest validation results including baseline failures, and a reviewed complete diff.

The skill is recommended because it produces all of that by construction, which is why agent-prepared PRs here tend to be substantially easier to review. A hand-written pull request that meets the same bar is equally welcome. What is not welcome, from a human or an agent, is a PR that claims a test result it did not produce.

The full contributor rules are CONTRIBUTING.md and docs/AGENTIC_CONTRIBUTING.md. Note one extra rule if you are changing the skills themselves: every change under .agents/skills/ or .claude/skills/ must include before/after behavioural evals with committed, sanitised results in the same PR, and CI checks that the evaluated contents match the submitted change.

No agent? That is completely fine

The guided issue forms ask for the same information, and a report filed by hand is worth exactly as much.

  • Open an issue — Gameplay, configuration or rendering bug if the game builds and runs but behaves or looks wrong; Build or installation problem if it will not install, build, launch or pass its self-test.
  • Check Known bugs first, in case it is already recorded.
  • For a security problem, use the security policy privately instead of opening a public issue.

Both forms end with a game-data check, for the same reason this page opens with one.
